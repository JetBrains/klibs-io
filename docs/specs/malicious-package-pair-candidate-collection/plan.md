# Plan: `malicious-package-pair-candidate-collection`

**Spec:** [spec.md](spec.md)

## Approach
A new physical table (`suspicious_package_pair_candidate`) in `core/package` stores the detected conflicts for a reviewer to work through. A *conflict* is one project in which a single `artifactId` is published under two or more `groupId`s; the table holds one row per `(project_id, artifact_id, group_id)` *entry* of such a conflict, plus reviewer-lifecycle columns (`status`, `notes`, `detected_at`). Detection is a single read-only native `@Query` over `package` (filtered `project_id IS NOT NULL`) that aggregates per entry and keeps only entries whose `(project_id, artifact_id)` spans more than one `group_id` (a window `COUNT(*) OVER (PARTITION BY project_id, artifact_id)` over the grouped rows), in the style of the existing native aggregation queries (`findAllKnownMavenCentralPackages` / `findDuplicateDescriptions`). A collector service performs a status-preserving upsert — load existing rows, apply a pure merge decision, `saveAll` — on the unique `(project_id, artifact_id, group_id)` key: insert new rows `PENDING`, refresh signal columns on existing rows, never touch reviewer `status`/`notes`, never delete. `derived_owner_login` is a pure string parse of `group_id` (`io.github.*` / `com.github.*` → lower-cased owner, else `NULL`).

A daily scheduled job in `app`, modelled on `RefreshDependentCountJob` (`@Scheduled(fixedRate)`, `@SchedulerLock`, `@ConditionalOnProperty`), invokes the collector's recompute. The first run seeds all pre-existing conflicts; no backfill. Build order is schema → collection logic → scheduling, each independently testable.

- **What:** Additive Liquibase changeset creating the table (`bigint` PK from a dedicated sequence, per the `maven_artifact` convention — `GenerationType.SEQUENCE` + `CREATE SEQUENCE … INCREMENT BY 50`; `project_id` `int` `NOT NULL` with FK to `project`; `artifact_id`/`group_id` `text`; `version_count` `int`; `first_release_ts`/`last_release_ts` `timestamp`; nullable `derived_owner_login`/`notes`; `status` `text` (enum stored as string); `detected_at` `timestamp`; unique index on `(project_id, artifact_id, group_id)`) plus the JPA `@Entity` that maps it (`project_id` a plain column, no `@ManyToOne`), the `PENDING`/`RESOLVED`/`IGNORED` enum, and a bare Spring Data repository over the entity.

DB tests live in `app` because `BaseUnitWithDbLayerTest` is a full `@SpringBootTest(classes = [Application])` and is not visible to `core/package`'s test source set.

## Milestone 2 — Detection query + owner parser + collector upsert
- **Files:** `core/package/src/main/kotlin/io/klibs/core/pckg/repository/SuspiciousPackagePairCandidateRepository.kt` (add native detection `@Query`), `core/package/src/main/kotlin/io/klibs/core/pckg/dto/projection/SuspiciousPackagePairView.kt` (new; projection interface + a data-class impl for pure tests), `core/package/src/main/kotlin/io/klibs/core/pckg/service/SuspiciousPackagePairCollector.kt` (new; holds the recompute entrypoint + `deriveOwnerLogin` and `merge` pure helpers), `core/package/src/test/kotlin/io/klibs/core/pckg/service/SuspiciousPackagePairCollectorUnitTest.kt` (new; pure-function tests), `app/src/test/kotlin/io/klibs/core/pckg/service/SuspiciousPackagePairCollectorDbTest.kt` (new; DB scenarios)
- **What:** Native `@Query` returning the conflict projection (per-entry `version_count`/`first_release_ts`/`last_release_ts`, cross-group filter, `project_id IS NOT NULL`; `COUNT(*)::int` so the projection maps to `Int`); the collector loads existing rows into a key map, applies the pure `merge` decision per detected entry, and `saveAll`s — inserting new rows `PENDING`, refreshing only signal columns on existing rows, never touching `status`/`notes`, never deleting; logs a run summary (inserted / signal-updated / total).
- **Validation:** `./gradlew :core:package:test` — pure-function unit tests (no DB) for `deriveOwnerLogin` (github hosts lower-cased, others null) and the `merge` upsert decision (fresh `PENDING` vs. status/notes/id/detected_at preserved with signals refreshed). `./gradlew :app:test` — DB-integration tests (`BaseUnitWithDbLayerTest`, `@Sql` seeds) for Scenario 1 (all entries `PENDING`), Scenario 2 (re-run preserves `RESOLVED` + `notes`, no duplicates), Scenario 3 (owner null vs. value), plus single-`groupId` ignored, `project_id IS NULL` skipped, FR-002 aggregates, and FR-011 (row kept after its `package` row removed).
- **Depends on:** Milestone 1

## Milestone 3 — Scheduled job + feature toggle
- **Files:** `app/src/main/kotlin/io/klibs/app/job/CollectSuspiciousPackagePairsJob.kt` (new), `app/src/test/kotlin/io/klibs/app/job/CollectSuspiciousPackagePairsJobTest.kt` (new). No production config change: the job reuses the existing `klibs.indexing` toggle (already defined in `application.yml`, default `false`), so no new property is added.
- **What:** Daily job (`@Scheduled(initialDelay = 0, fixedRate = 1, timeUnit = DAYS)`, `@SchedulerLock(name = "collectSuspiciousPackagePairsLock", lockAtMostFor = "1h")`, `@ConditionalOnProperty("klibs.indexing", havingValue = "true")` — reusing the shared indexing toggle, not a dedicated per-job flag) that calls `LockAssert.assertLocked()` then the collector's recompute; recompute stays independently callable for manual re-seeding.
- **Validation:** `./gradlew :app:test` — a unit test (no Spring context) that constructs the job with a mocked collector, bypasses ShedLock via `LockAssert.TestHelper.makeAllAssertsPass(true)`, invokes the scheduled method, and verifies it delegates to `recompute()`. A full `@SpringBootTest` wiring check is deliberately avoided: enabling `klibs.indexing=true` would activate and schedule every indexing job (`@EnableScheduling` is on), and the collector's behaviour is already covered by M2's DB tests.
- **Depends on:** Milestone 2
